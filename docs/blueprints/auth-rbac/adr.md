# ADR — 인증은 Supabase Auth를 쓴다 (버전·가격 확인일 2026-10)

## 맥락
- 모든 모듈이 같은 `org_id` 테넌시와 RLS를 쓰고, 판정(`has_permission`)은 DB 한 곳에 둔다. 사용자·세션은 DB 안(`auth` 스키마)에 있는 편이 RLS와 직결된다.
- 한국 서비스는 카카오·네이버 로그인이 사실상 필수다.

## 선택
Supabase Auth(GoTrue, MIT *[지식 — 라이선스·버전 공식 문서 재확인]*)를 쓰고, 조직·멤버십·역할·초대는 앱 테이블(`data.md`)로 직접 둔다. 근거 원형: platform-docs CORE_SPEC#2 · core_lite(가입 트리거·멤버 함수).

## 대안
| 대안 | 장점 | 채택 안 한 이유 |
|---|---|---|
| Clerk | 로그인·조직 UI 컴포넌트와 조직 기능 내장 | 상용 MAU 과금(수치 확인 필요), 사용자 원본이 DB 밖이라 RLS와 직결 안 됨 |
| Keycloak | 완전 셀프호스트, SAML·OIDC·브로커링 (Apache-2.0, 최신 26.8.1은 단일 출처 — 확인 필요) | 별도 서버 운영 부담, 1인·소규모 MVP에 과함. 엔터프라이즈 SSO 요구가 생기면 재검토 |

## 소셜 로그인
| 공급자 | 상태 |
|---|---|
| Google | 기본 제공 공급자 *[지식 — 확인 필요]* |
| 카카오 | 기본 제공 여부 *확인 필요* |
| 네이버 | 기본 제공이 아니면 커스텀 OIDC로 연결 — **OIDC 지원·계약 확인 필요**. 불가하면 서버 OAuth 어댑터로 연결(결정) |

## 결과
- 사용자·세션 원본은 Supabase가 책임지고 앱은 `profiles`·`memberships`를 소유한다. 이후 Supabase 종속이 부담되면 `auth.users.id`를 키로 이전한다.
- 확장 지점: 본인인증(PASS 등), 조직 MFA 강제(aal 확인), 도메인 자동 가입, 커스텀 역할 — MVP 제외.
